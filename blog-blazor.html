Choosing Blazor over React: a .NET team's perspective

Why we chose Blazor WebAssembly over React for our event management platform, and where the trade-offs actually land for a team that lives in the .NET ecosystem.

When we started building a new event management platform earlier this year, the frontend technology choice was the first real decision. We're a .NET team. Our backend was always going to be ASP.NET Core. The question was whether the frontend should be React (the industry default) or Blazor WebAssembly (the .NET-native option).

We chose Blazor. Six months in, here's where that decision has landed.

The case for Blazor was operational, not ideological

The argument for Blazor wasn't "React is bad" — React is a mature, well-supported framework with an enormous ecosystem. The argument was about our team, our stack, and our delivery model.

We're a small consultancy that delivers end-to-end. The same developers who design the data model also build the API, the frontend, and the deployment pipeline. Introducing React would have meant maintaining two language ecosystems (C# and TypeScript), two build systems (dotnet and npm/webpack/vite), two sets of testing tools, and two mental models for how state flows through the application.

With Blazor, the entire stack is C#. Shared DTOs between client and server. One set of tooling. One language for everything from Entity Framework queries to UI component logic. For a team of our size, that operational simplicity is worth more than React's ecosystem advantages.

Where Blazor genuinely shines

Shared models. The same C# classes define the API request/response shapes and the client-side view models. When we add a field to a DTO, both sides know about it immediately. No JSON serialisation mismatches, no drift between TypeScript interfaces and C# models.

Strong typing throughout. Blazor components are strongly typed in a way that JSX can't match. Component parameters, event callbacks, and cascading values are all checked at compile time. This catches an entire category of bugs that would surface at runtime in React.

PWA support out of the box. Blazor WASM supports progressive web app features natively — service workers, offline caching, installability. For our event platform, where attendees need the app to work in a venue with unreliable Wi-Fi, this was essential. The PWA template gave us a working offline-capable app with minimal configuration.

Component model. Razor components are straightforward to compose. The lifecycle is simpler than React's useEffect dependency arrays, and the rendering model is predictable. For developers who already know Razor from server-side work, the learning curve is minimal.

Where the trade-offs land

Initial load time. This is Blazor WASM's most cited weakness, and it's real. The initial download includes the .NET runtime, which adds several megabytes to the first load. For our event app, we mitigate this with a loading screen and aggressive caching — after the first visit, subsequent loads are near-instant. For a public marketing site with SEO requirements, this would be a dealbreaker. For an authenticated line-of-business app, it's acceptable.

Ecosystem size. React has thousands of component libraries, Blazor has dozens. We've occasionally had to build something that we could have installed as a React package. In practice, this has been less painful than expected — the components we need (data grids, form validation, modals) exist in mature Blazor libraries, and the simpler components are quick to build.

Hiring and community. Finding React developers is easier than finding Blazor developers. For a consultancy our size, this isn't an immediate concern — but it's a real factor for larger organisations considering Blazor for team-scale projects.

The right frontend framework is the one that lets your team deliver reliably with the skills they have. For a .NET team building authenticated line-of-business apps, Blazor removes an entire category of integration complexity.

When we'd still choose React

Blazor isn't the right choice for everything. For a content-heavy public website that needs fast initial loads and strong SEO, server-rendered React (Next.js) or even plain server-side Razor Pages would be better choices. For a project with a dedicated frontend team that already knows React and TypeScript, introducing Blazor would create unnecessary friction.

Our recommendation is specific: if your team is .NET-native, your application is authenticated, your users will return repeatedly (so the initial load cost is amortised), and you value full-stack type safety — Blazor WebAssembly is a genuinely productive choice that eliminates real operational complexity.

Six months in

The event platform is in production, the codebase is clean, and we haven't hit a situation where we wished we'd chosen React. The shared model layer alone has prevented dozens of bugs that would have required manual TypeScript-to-C# synchronisation. The PWA works offline. The components render predictably.

Blazor isn't the future of all web development. But for .NET teams building line-of-business applications, it's a legitimate first choice — not a compromise.

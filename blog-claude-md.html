Every project we run now starts with a CLAUDE.md

AI-assisted delivery is only as good as the brief you give it. Here's the file we now write before any code, and what a year of doing it has taught us.

A year ago, the first thing we wrote on a new project was a feature specification. Now it's a file called CLAUDE.md that lives at the root of the repository.

The two documents look superficially similar — both describe the project, both list constraints, both mention the tech stack. But the audience is different, and that changes what goes in. A feature spec is written for a developer who will read it once, ask questions in Slack, and then start coding. A CLAUDE.md is written for an agent that reads it on every interaction, can't ask follow-up questions in real time, and will silently do the wrong thing if you're vague.

That difference in audience is what we underestimated when we started.

What stopped working

For the first six months of using Claude Code in production, our briefs were the same documents we'd always written. The results were predictable: agents made plausible but wrong decisions. They created new files instead of editing existing ones. They added a build step to a project that didn't have one. They refactored stable code "for clarity" when asked to fix a one-line bug. They invented framework idioms that don't exist. They forgot the colour palette.

None of these were model failures in the strict sense. Claude was doing its best with the information available — and the information was incomplete. Our briefs assumed a developer who would notice the absence of a package.json, infer that the project was a static site, and act accordingly. An agent making one-shot decisions doesn't have that luxury. It works from what's in front of it.

What goes in

A CLAUDE.md that earns its place in our repos tends to have four sections, in roughly this order:

Project overview. Two sentences, no marketing copy. What this is, who it's for, what it isn't. "Static B2B marketing site, no build system, no templating engine." The negative space matters as much as the positive — saying what isn't there prevents a whole category of well-meaning mistakes.

Development. How to run the thing. How to test the thing. Which scripts exist, which don't. If npm test doesn't work, say so explicitly, otherwise the agent will run it, get an error, and waste a turn debugging a non-issue.

Architecture. The file layout, the module boundaries, the conventions that aren't enforced by tooling. Where shared chrome lives, how routing is wired, which directory holds tests. Anything a developer would learn by spending a week in the codebase, written down so an agent can learn it in thirty seconds.

Conventions. The project-specific rules that override defaults. "All links are relative paths." "Forms submit to Formspree, no backend." "Don't describe the team as small." These are the rules we used to communicate verbally — the ones that lived in the heads of the senior engineers. They have to be written down now, because the agent doesn't have a head to live in.

What we deliberately leave out

A bad CLAUDE.md is bloated. It tries to anticipate every question, ends up at four thousand words, and the agent treats half of it as background noise. Three categories of content we've learned to leave out:

Things the code already says. If a function is called ValidateUkPostcode and it has a regex, we don't write a paragraph about postcode validation. The code is the source of truth. The brief points at it.

Things the agent can discover. File listings, dependency lists, the contents of package.json. The agent can read these directly. Repeating them in the brief creates a synchronisation problem and nothing else.

Aspirations. "We want to eventually move to a headless CMS" doesn't help an agent making changes today. It either acts on the aspiration prematurely or ignores it entirely. Roadmap items belong in roadmap documents, not delivery briefs.

If we can't write a clear CLAUDE.md, that's usually a sign we don't understand the project clearly enough ourselves — that the architecture is muddled, the conventions are inconsistent, or the constraints are implicit.

The discipline this forces

Writing a useful CLAUDE.md turns out to be the same skill as writing a useful brief for a junior developer joining the team. The questions you have to answer are the same: what is this, how do I run it, where do things live, what's the local culture, where are the landmines.

The difference is that a junior developer can ask. An agent can only work from what's there. So if we can't write a clear CLAUDE.md, that's usually a sign that we don't understand the project clearly enough ourselves — that the architecture is muddled, or the conventions are inconsistent, or the constraints are implicit. Writing the brief surfaces those problems before they become bugs.

That feedback loop is the part we didn't expect. We started writing CLAUDE.md files to make our agents more effective. We kept writing them because they made our projects more legible to ourselves.

What it looks like in practice

On a recent Umbraco rebuild, the CLAUDE.md ran to 380 lines. It described the package boundaries between the marketing site and the member portal, the conventions for content types and document type aliases, the localisation strategy, the deployment pipeline, and a list of decisions we'd already made and didn't want to revisit. It took two hours to write and probably saved a week of back-and-forth.

For the static site you're reading this on, the CLAUDE.md is sixty lines. The project is small. The conventions are few. The brief reflects that.

There isn't a template, because every project has different shapes of complexity. There is, however, a discipline: write down the things that matter, leave out the things that don't, and update it when reality changes. The same discipline that makes any document useful, applied to a document the agent reads every single time.

One file, not a folder

A pattern we tried and abandoned: splitting the brief into many files. ARCHITECTURE.md, CONVENTIONS.md, DEVELOPMENT.md, all referenced from a top-level CLAUDE.md. It looked tidy. It performed worse.

Agents don't always follow links. Even when they do, the cost of a missed reference is high — a convention that wasn't loaded leads to a convention that wasn't applied. A single file at the root, read on every turn, removes that failure mode entirely. The cost is a slightly longer file. The benefit is consistency.

Our rule of thumb: if it changes the agent's behaviour, it goes in CLAUDE.md. If it doesn't, it doesn't need to be written down.

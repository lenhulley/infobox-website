.NET Aspire two years on: where cloud-native .NET actually landed

Aspire reached general availability in May 2024 as a developer-experience improvement. The 13.4 release in 2026 is a different product — and the case for picking it up again is stronger than the case for putting it off.

Aspire reached general availability at Microsoft Build on 21 May 2024. At the time the framing was modest: a stack of templates, NuGet packages, and a web dashboard to make running multiple .NET services on a developer machine less painful. The Aspire 13.4 release in 2026 looks like a different product. The AppHost now accepts TypeScript, the CLI is first-class, the deployment story uses named publishers instead of an intermediate manifest, and the Kubernetes integration treats AKS as a planned deployment target rather than a worked example. Anyone who looked at Aspire in late 2024 and decided to wait should look again.

The AppHost is the project

At Aspire's core is the AppHost: a small project that describes the composition of a distributed application — services, databases, queues, caches, the lot — using a fluent API. The builder.AddProject<>(), AddPostgres(), AddRedis() pattern that started as a developer-time convenience now drives deployment, observability, and increasingly the production topology itself. The deliberate decision was to make the AppHost the single source of truth for how the pieces fit together, not just for the inner loop. Two years of releases have followed that line of thinking.

The 13.4 release promotes the TypeScript AppHost to general availability, having shipped it as a preview in 13.2. The application model is unchanged — the difference is the authoring surface. Teams with a Node-based stack alongside .NET services no longer need to maintain a parallel C# project just to participate in Aspire. The architectural argument is that Aspire's value is the orchestration model, not the language of its definition.

The CLI is no longer optional

Aspire 9.4, in mid-2025, took the aspire CLI out of preview. Before that, “use Aspire” effectively meant “use Visual Studio or its equivalent.” After 9.4, project creation, run, watch, publish, and deploy are first-class commands. This matters less for the inner-loop experience — IDEs were always going to handle that — and more for everything around it: scripting CI builds, standing up ephemeral environments, packaging integration tests that need a real Postgres and a real message broker rather than substitutes.

The CLI also unlocks the next several pieces. aspire publish and aspire deploy aren't aliases for dotnet build; they are the documented extension points where Aspire hands off to whatever target the team is shipping to.

Publishers replaced the manifest format

Earlier versions of Aspire used an intermediate manifest format — a JSON description of the application that downstream tools (azd, others) would consume. As of Aspire 9.2, publishers became the supported extensibility point, plugging directly into the application model to produce Docker Compose files, Kubernetes manifests, Azure resources, or anything else a team's environment requires. aspire publish serialises resources by invoking each registered PublishingCallbackAnnotation in declaration order; aspire deploy runs publish first, then invokes DeployingCallbackAnnotation handlers in the same way.

The practical effect is that the AppHost becomes the description of the application's topology end to end. A resource declared once gets the local sandbox, the deployment artefacts, and — through the same metadata — the dashboard wiring. That is a meaningful contrast to the prevailing infra-as-code pattern, where the topology is described twice (once for developers, once for ops) and the two descriptions drift.

Kubernetes is no longer an aside

The Kubernetes story is where 13.4 makes its biggest leap. The release adds first-class support for typed cert-manager resources, the Gateway API and Azure Application Gateway for Containers on AKS, arbitrary Kubernetes manifest resources for the things Aspire's resource graph doesn't model directly, and external Helm chart installation as part of the deployment pipeline. The Helm surface itself is cleaner: a single WithHelm(...) call replaces an older split configuration.

The shift is from “Aspire can target Kubernetes if you know what you're doing” to “Aspire treats Kubernetes-on-Azure as a planned, documented deployment path.” That is a different value proposition. Teams choosing between Azure Container Apps and AKS for an Aspire application no longer need to weigh Aspire support as one of the factors — both targets are now expected.

Observability without ceremony

The other part of the Aspire pitch that has held up is service defaults. The pattern hasn't changed much since GA: a ServiceDefaults project, referenced by every service, calls a single ConfigureOpenTelemetry method that wires up logging, tracing, and metrics through the .NET OpenTelemetry SDK. Telemetry exports via OTLP by default; the Aspire dashboard ingests it locally during development; the same exporter aims at Application Insights or any other OTLP-compatible backend in production.

The interesting consequence is what teams have stopped writing. The custom telemetry middleware, the per-project log enrichers wired by hand, the dashboards built service by service — most of that ceremony has gone, replaced by the framework default. Service defaults are also usable on their own, without the AppHost or orchestration, which makes the OpenTelemetry-on-.NET path Aspire defines genuinely portable.

The interesting design choice in Aspire is that the AppHost describes the application once, and the toolchain — dev loop, deployment, observability — follows from that description. The longer the project lives, the more that single description earns its keep.

Where Aspire fits — and where it doesn't

Aspire is not a runtime, not a service mesh, not a replacement for Kubernetes operators or Bicep. It is a way to describe a .NET-based distributed application in code and have a consistent toolchain follow from that description. It earns its keep when the application has more than two or three services and at least one supporting resource (database, cache, queue) that has to behave the same way locally and in production.

It is a less obvious fit for single-service applications, or for shops where the .NET layer is one tier inside a larger non-.NET system. In those cases the AppHost can become a piece of orchestration that competes with whatever the rest of the platform is already doing. The TypeScript AppHost narrows that gap; it does not close it.

Bottom line

The cloud-native .NET picture two years ago was a developer-experience improvement on top of the same Kubernetes-or-Container-Apps decision a team would have made anyway. In 2026 it is closer to a coherent stack. The AppHost is the topology description; the CLI is the entry point; publishers and the deploy command are the seam where Aspire hands off to the target environment; service defaults and OpenTelemetry are the observability story. The pieces fit together in a way they did not when Aspire shipped.

The most useful thing a team that shelved Aspire in 2024 can do is read the 13.4 release notes and decide whether the gaps that put them off then are still gaps. For most .NET-centred shops shipping more than one service, they aren't.

Built-in OpenAPI in .NET 10: where the ASP.NET Core API contract story finally lands

.NET 10 ships OpenAPI 3.1, YAML output, XML doc integration, a proper transformer model and Native AOT support — all in the first-party package. The Swashbuckle decision finally has a default answer.

For a decade, the default way to put an OpenAPI document on an ASP.NET Core API was to install Swashbuckle, configure its services, wire up the middleware, and accept that everything Swagger-related was a community package with its own release cadence. It worked. It was also a small but persistent reminder that the framework gave you the surface area and the community gave you the contract.

In .NET 9, Microsoft ended that arrangement. The default web API template stopped shipping Swashbuckle and pulled in Microsoft.AspNetCore.OpenApi instead. .NET 10, which went GA as a Long-Term Support release on 11 November 2025 with support through 14 November 2028, is the version where that decision has fully matured.

What ships in the box

Microsoft.AspNetCore.OpenApi in .NET 10 generates OpenAPI 3.1 documents by default, up from 3.0 in .NET 9. The version bump is more consequential than it sounds: OpenAPI 3.1 aligns the schema model with JSON Schema draft 2020-12, which means the contract a .NET API publishes is now structurally compatible with the JSON Schema dialect that the rest of the tooling world has settled on. Reference resolution, descriptions alongside $ref, and nullable handling all behave the way contemporary linters and code generators expect.

The basic wiring is still two lines: builder.Services.AddOpenApi() and app.MapOpenApi(), exposing the document at /openapi/v1.json. Swap the extension for .yaml or .yml in the route template — app.MapOpenApi("/openapi/{documentName}.yaml") — and the document is emitted as YAML at runtime. That addition lands in .NET 10. The document name is a route parameter, so a single API can publish v1.json, v2.json and internal.json from the same pipeline by registering multiple named documents with AddOpenApi("v2").

XML comments are no longer a separate problem

Pulling XML doc comments into the OpenAPI document has historically required configuring Swashbuckle to read the file the C# compiler emits, then handling the case where it isn't there in CI. .NET 10's OpenAPI generator does this automatically once the project enables GenerateDocumentationFile. Triple-slash comments on controllers, minimal API methods, classes and properties — including properties on [AsParameters] binding types — flow into the generated document with no additional configuration.

The transformer model

Customising the generated document is now done through three transformer types, with a defined execution order:

  • Schema transformers — one CLR type maps to one schema. These run first, as schemas are registered to the document.
  • Operation transformers — one operation is one path plus HTTP method. These run as operations are added.
  • Document transformers — see the entire document. These run last.

The transformer context in .NET 10 also exposes a GetOrCreateSchemaAsync method that resolves the schema for a CLR type using the same code path the framework would, and a Document property that allows any transformer to add components via AddComponent. That is exactly the seam the earlier transformer API was missing — there was no first-party route to dynamically add a schema from inside a transformer without reconstructing what the framework had already built.

WithOpenApi is going away

.NET 10 also deprecates the WithOpenApi() extension method on minimal API endpoints. Calls still compile and run, but the compiler now emits diagnostic ASPDEPR002 along with a standard Obsolete warning. The breaking-change notice frames the rationale plainly: WithOpenApi duplicated functionality the document-generation pipeline already provides.

The migration path for projects on the built-in stack is to register an operation transformer with AddOpenApiOperationTransformer. Swashbuckle and NSwag users keep their respective IOperationFilter and IOperationProcessor extension points; only the built-in shortcut is being removed.

Build-time generation, not just runtime

The runtime endpoint is the visible part of the new stack, but the more interesting change for teams that take API contracts seriously is build-time generation. Adding Microsoft.Extensions.ApiDescription.Server to a project causes the OpenAPI document to be emitted to the obj directory on every build. The OpenApiDocumentsDirectory MSBuild property redirects that output; OpenApiGenerateDocumentsOptions controls the filename and the OpenAPI version emitted.

That is the configuration that matters for production discipline. Once the document is part of the build, it can be committed alongside the source, diffed in pull requests, linted by Spectral or any other OpenAPI linter, and consumed by client-generator pipelines without spinning up the API host. Contract changes become visible code-review surface. The same outcome was achievable with Swashbuckle plus a CI step, but it required configuration most teams skipped.

Native AOT is in scope

In earlier versions, the moment a project enabled Native AOT the OpenAPI story broke — Swashbuckle's generation relied on reflection patterns the trimmer couldn't preserve. The built-in generator in .NET 10 is AOT-compatible. That makes OpenAPI documentation viable for minimal API services published as small, self-contained AOT executables — the deployment model that .NET 9 made attractive and .NET 10 makes practical for production services.

IOpenApiDocumentProvider

One quieter addition: IOpenApiDocumentProvider is now available through the DI container. Injecting it gives any service access to the generated document outside the context of an HTTP request — useful for background workers that need to publish contract metadata, for tools that produce SDKs from the running configuration, or simply for unit tests that want to assert on the shape of a document without booting Kestrel.

The thing that changed in .NET 10 isn't a single feature. It's that "Swashbuckle or the new thing?" no longer needs to be re-litigated on every new project.

Where Swashbuckle still fits

The package isn't dead. Swashbuckle 10 supports .NET 10 and offers opt-in OpenAPI 3.1. The reason to install it now is narrower: serving the Swagger UI. The built-in package generates the document but does not ship an in-browser explorer — that is a deliberate scope decision. Projects that want a UI can add Swashbuckle.AspNetCore.SwaggerUI and point its SwaggerEndpoint at the built-in /openapi/v1.json route, or adopt one of the newer alternatives such as Scalar, which is increasingly the default in the .NET community.

What the default looks like in 2026

For new ASP.NET Core services, the calculus has changed. The .NET 10 API template does not include Swashbuckle, and there is no longer a feature gap that justifies adding it back for document generation. OpenAPI 3.1, XML doc integration, transformer-based customisation, YAML output, build-time emission and AOT support are all in the first-party package.

For services on .NET 8 — the previous LTS, supported until November 2026 — the migration calculus is different: stay on Swashbuckle until the .NET 10 upgrade, then make the swap deliberately. The WithOpenApi deprecation is the natural cue to plan that swap alongside the runtime upgrade rather than as a separate piece of work.

The signal in .NET 10 is not that the new package finally caught up with Swashbuckle. It's that the new package now does things Swashbuckle never quite did: build-time emission as a first-class concern, AOT compatibility, schema fidelity with the wider JSON Schema world. The contract is, at last, part of the framework.

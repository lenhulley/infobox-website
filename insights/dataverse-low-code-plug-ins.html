Dataverse low-code plug-ins: where Power Fx fits, and where it doesn't

Power Fx as a Dataverse extensibility model is two years into preview, with the instant variant already retired. A look at where the low-code surface fits — and where the C# plug-in still has to do the work.

For nearly two decades, the answer to "how do I run server-side logic in Dataverse?" has been one thing: a compiled .NET assembly implementing IPlugin, signed, uploaded through the Plug-in Registration Tool, and bound to a step in the message pipeline. Microsoft's documented alternative — low-code plug-ins authored in Power Fx — has been visible in the Dataverse accelerator app since 2023, and it is still in preview at the time of writing. That gap between announcement and general availability is worth taking seriously. It says something about where this capability fits in a serious extensibility strategy.

The model itself is simple. A low-code plug-in is a Power Fx expression stored inside Dataverse and executed server-side in response to an event. Microsoft documents two flavours: instant plug-ins, manually invoked with custom input and output parameters; and automated plug-ins, which fire on Create, Update, or Delete events against a chosen table. Both are authored inside the Dataverse accelerator app — a model-driven app that ships preview tooling. The accelerator is automatically installed in environments created from 1 October 2023 onwards; older environments need it installed manually from the Power Platform admin centre.

That much matches the marketing. The interesting nuance is what Microsoft has documented about the trajectory.

The instant pivot

The "Tips when working with low-code plug-ins" page on Microsoft Learn carries an unusually direct statement: "Instant low-code plug-ins are deprioritized and aren't being delivered as a feature. Instant low-code plug-ins are replaced with functions." The replacement — Dataverse functions — is itself in preview.

Read carefully, that line is a vendor admission that half of the original low-code plug-in pitch has been quietly retired. For teams who built a strategy around instant plug-ins as a reusable, callable unit of server-side logic, the migration path now points to a different feature. Anyone evaluating the technology today should plan around automated plug-ins only, and treat any tutorial that demonstrates instant plug-ins as historical context.

What the runtime actually allows

The Power Fx dialect used in low-code plug-ins is a subset of the one used in canvas apps, not a superset. The reference page documents the gap explicitly: Clear, ClearCollect, Update, UpdateIf, GroupBy, Search, the form-related functions, and the device-sensor functions are all unsupported. Defaults() — useful for instantiating an empty record before patching it — does not exist either; the documented workaround is to use Collect() against a typed variable.

Two operational limits matter more than the formula gaps in practice.

The first is the two-minute timeout. Any plug-in execution that exceeds it fails with the message "Operation not allowed as plugin execution exceeded maximum allowed time". C# plug-ins share the same ceiling, but a C# author has access to lower-level optimisation that a Power Fx expression does not. A handful of connector calls inside an automated plug-in can consume a surprising amount of that envelope.

The second is the infinite-loop trap. Patch() inside an automated plug-in registered on Update will, if it targets the same table, trigger the plug-in again. Microsoft calls this out specifically and recommends Set() against local context, or a Patch() against a different table or record. The C# equivalent — checking the Depth property on the execution context — is not exposed to Power Fx, so the discipline has to come from the author rather than from a runtime check.

Where connectors change the equation

The genuine differentiator over the C# plug-in model is connector access. A C# plug-in runs inside the Dataverse sandbox; outbound HTTP requires explicit configuration, the managed-identity story is non-trivial, and developers end up writing similar authentication boilerplate for every external call. A low-code plug-in can invoke any Power Platform connector — first-party, certified, or custom — via a connection reference deployed with the solution. The published examples show MSN Weather, email via templates, and in-app notifications all being called from inside automated plug-ins.

Microsoft does note that "not all connector actions are supported at this time", and that connection references must be created before the plug-in is authored. But for scenarios that would otherwise require either a Power Automate cloud flow with its own latency budget, or a custom Azure Function with its own deployment story, this is a meaningfully simpler model.

When the C# plug-in still wins

The Power Fx model is not a replacement for everything IPlugin offers. Anywhere the following matters, the compiled route remains the right answer:

Pre-image and post-image manipulation. IPluginExecutionContext exposes PreEntityImages and PostEntityImages, which make pre-validation and field-change auditing straightforward. The low-code surface does not expose equivalents.

Transactional control and shared variables. Multi-step transactions, plug-in chaining via SharedVariables, and depth-aware recursion guards are all C# territory.

Performance-critical execution. Community benchmarks have consistently measured Power Fx plug-ins running noticeably slower than equivalent C# logic. For high-volume integrations or hot-path validation, that cost is not negligible.

Production-grade reliability today. Until the feature moves out of preview, the documentation itself states that preview features "aren't meant for production use and may have restricted functionality". Reading past that line is a business risk to own deliberately, not a technical decision to default to.

The interesting question is not "is Power Fx fast enough to replace C# plug-ins?" It's "which logic genuinely belongs to a maker, and which still belongs to a developer with a signed assembly and a CI pipeline?"

The honest read

Dataverse low-code plug-ins earn their place in two specific situations. The first is connector-driven side effects on table events — sending a notification, posting to Teams, calling out to a SaaS — where the C# alternative would be heavyweight for what the rule is doing. The second is logic that genuinely belongs to a maker rather than a developer, where the cost of building, signing, and registering a .NET assembly is out of proportion to the constraint being encoded.

Outside those two zones, the picture is less generous. The retirement of instant plug-ins, the preview status that has not shifted in over two years, the Power Fx feature gaps, and the missing execution-context primitives all point in the same direction. Low-code plug-ins are a complement to compiled extensibility in Dataverse, not a successor to it.

Teams looking at the technology should plan accordingly: pilot the automated variant against a defined business event, design around the documented constraints rather than discovering them in production, and assume the pro-code plug-in path will keep doing the heavy lifting for the foreseeable future.

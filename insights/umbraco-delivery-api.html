Three years of the Umbraco Delivery API: where headless-on-the-CMS lands

Umbraco 12 shipped a first-party Content Delivery API in June 2023. Three years and four major versions later, the question of whether to reach for Heartcore, a third-party headless CMS, or Umbraco itself has a different shape than it used to.

For years the “is Umbraco headless?” conversation had a tidy two-product answer. Umbraco CMS rendered Razor views; Umbraco Heartcore, the managed SaaS offering, delivered JSON over HTTP. If you wanted a decoupled front end against an Umbraco editorial experience, Heartcore was the path, and the only path that was first-party.

That stopped being true with Umbraco 12, released on 29 June 2023, which shipped the Content Delivery API as a generally available feature of the open-source CMS. Three years on, with Umbraco 13 carrying the long-term-support label, Umbraco 17.4.0 released on 19 May 2026, and the Bellissima backoffice rewrite having landed in Umbraco 14, the architectural conversation around Umbraco and JSON has moved on. It is worth stopping to look at what is actually in the box, and where it does and does not change the calculus.

What ships out of the box

The Content Delivery API is exposed at /umbraco/delivery/api/v2/content with a companion media endpoint at /umbraco/delivery/api/v2/media. An OpenAPI description is published at /umbraco/swagger, which makes client generation straightforward against the standard .NET, TypeScript, and Java tooling that already knows how to read it.

Queries are shaped by a small set of well-documented parameters. fetch applies a structural selector — fetch=children:{id}, fetch=descendants:{id}, fetch=ancestors:{id} — against either the GUID or the URL path of a content item. filter and sort handle the predicate work. expand controls which nested properties are inlined into the response, with the syntax expand=properties[$all] to expand everything expandable, or expand=properties[alias1,alias2] to expand a specific subset. fields mirrors that syntax for output projection. Combined, those four parameters cover the common shape of a content query without forcing custom code on either end.

Output caching is opt-in and, importantly, tag-aware. When responses are cached, Umbraco tags them with identifiers tied to the underlying content; when an editor publishes a change, the relevant tags are evicted rather than the entire cache. For a content surface that traditionally lived behind a CDN with manual purges, that is a meaningful operational improvement.

Authentication is the part that matters

The most overlooked part of the Delivery API is its auth story, because the headline feature is the unauthenticated endpoint. By default the API only exposes content that is not protected by an Umbraco public-access rule. Anything behind a member group is invisible — not 401, not 403, just absent — until member authorisation is explicitly enabled in appsettings.json.

When it is enabled, the model is OpenID Connect: the Authorization Code Flow with PKCE for interactive member sessions, and the Client Credentials Flow for server-to-server consumers. The latter is the interesting one. Client Credentials in this context map an API consumer to an “API Member” identity inside Umbraco; the consumer exchanges its client ID and secret for an access token at the Delivery API’s token endpoint, then uses that token as a bearer credential against the protected content endpoints. The token effectively impersonates the API Member, so the existing public-access rules continue to define what the consumer can read.

Two operational details are worth flagging. The first is that toggling member authorisation requires a rebuild of the DeliveryApiContentIndex through the Examine management dashboard, because the index needs to reflect the new protection state. The second is that the documentation is explicit about reusing access tokens for their full lifetime rather than minting a new token per request — sensible for performance, but easy to miss in a first integration.

What Bellissima changes about the architecture

The other architectural shift sits behind the scenes. Umbraco 14 replaced the long-standing AngularJS backoffice with a rewritten one, codenamed Bellissima, built on Web Components, Lit, TypeScript, and Vite. The official documentation is direct that the backoffice now consumes a Management API the same way a third-party SPA would: Umbraco’s own administrative interface is, in effect, a headless client of its own server.

The downstream effect for teams building on the platform is that the Delivery API is no longer a side-feature of an otherwise monolithic CMS. It is the public-facing sibling of an architecture that is now wholly decoupled internally. That is also why Umbraco explicitly allows extension authors to use any framework that compiles to Web Components — React, Vue, Svelte, or plain Lit — rather than forcing them onto the in-house stack. The same pattern applies to the public front end: the choice of Next.js, Nuxt, Astro, SvelteKit, or Razor is no longer constrained by the CMS.

What it does not replace

Three caveats are worth stating plainly.

First, the Delivery API is REST, not GraphQL. The combination of fetch, filter, expand, and fields covers a large share of practical queries, but federation across multiple back-ends, deeply nested ad-hoc selections, and schema-first tooling remain GraphQL strengths. Heartcore, by contrast, exposes a GraphQL endpoint alongside its REST surface; teams that have built around GraphQL clients should keep that on the comparison table.

Second, the built-in endpoints are opinionated. The escape hatch is IApiPublishedContentCache and IApiContentResponseBuilder, both of which are documented in the “Custom Delivery API endpoints” reference and let .NET developers compose responses that the default routes do not produce. That is a developer task, not an editor task, and worth scoping early when the off-the-shelf shape does not fit.

Third, the Delivery API is read-only. Content authoring still happens through the Bellissima backoffice or, for programmatic ingestion, the Management API. Anyone planning a write-through path from a front-end should use the Management API and treat the Delivery API as the read surface it was designed to be.

The architectural question for an Umbraco-backed front end has shifted from “which Umbraco product” to “which hosting model.” The capability gap between the open-source CMS and the managed headless service has narrowed to the points that are genuinely about operations rather than features.

The honest read

The Delivery API is no longer a preview, no longer a side experiment, and no longer the reason to default to a third-party headless CMS for an Umbraco-fronted project. With Umbraco 13 supported through December 2026 and Umbraco 17 lined up as the next long-term-support release on .NET 10, both supported versions ship the same API surface, on the same release cadence as the rest of the CMS.

That does not mean the Delivery API is the right answer for every project. Heartcore continues to make sense when nobody on the team wants to operate a .NET host. A third-party headless CMS still makes sense when content already lives elsewhere or when GraphQL federation is a hard requirement. Razor still makes sense when the front end is server-rendered and SEO-driven and the editor experience benefits from preview-as-you-edit.

The point is that the choice now sits on operations and team shape rather than on what the platform can or cannot do. For a .NET team comfortable hosting Umbraco, the Delivery API closes the last gap that used to push that decision toward a different product.
